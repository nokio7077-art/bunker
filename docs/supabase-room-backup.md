# Резервное сохранение комнат Бункера в Supabase

Основное хранилище остаётся локальным: `.data/rooms.json` с резервной копией. Дополнительное облачное хранилище создаёт контрольную точку активных комнат в отдельном проекте Supabase. **Не используйте существующий проект Cosmopolitan Atlas:** комнаты содержат секретные токены игроков.

## Однократная настройка

1. Создайте **отдельный** проект Supabase, например `bunker-backup`.
2. В SQL Editor этого проекта выполните `sql/bunker-room-snapshots.sql`.
3. В настройках **Render → bunker-online → Environment** задайте `SUPABASE_URL` (Project URL) и `SUPABASE_SECRET_KEY` (новый `sb_secret_...` из Supabase Project Settings → API Keys). Не отправляйте ключ в чат, не сохраняйте в GitHub и не добавляйте в HTML.
4. Выполните redeploy Render и проверьте логи: не должно быть сообщения `Supabase checkpoint failed`.
5. Создайте тестовую комнату, затем убедитесь в Supabase Table Editor, что у `bunker_room_snapshots` есть строка `id = active`. Проверьте восстановление только на тестовой комнате.

Без обеих переменных облачное сохранение отключено, игра работает в текущем локальном режиме. Если облако временно недоступно, активные комнаты продолжают работать; их данные остаются на локальном диске. Попытки облачного сохранения продолжатся позднее. При запуске новый сервер сначала пробует восстановить облачную контрольную точку и лишь затем принимает игроков. Если локальное сохранение свежее, оно имеет приоритет.

## Важные ограничения

- В облаке хранится последний снимок всей комнаты, **включая секретные карточки, токены и коды восстановления**. Доступ предоставляется только серверу через secret key. Используйте отдельный проект.
- Синхронизация с облаком асинхронная: при мгновенном сбое хостинга последние доли секунды прогресса могут отсутствовать. Сценарий с одновременной работой нескольких независимых экземпляров сервера не поддерживается.
- Пропущенное сохранение из-за сбоя облака восполняется после следующего успешного локального сохранения. Для коротких игровых сессий этого достаточно, но это не система строгих транзакций между хостами.
- Если обе локальные копии повреждены, сервер намеренно не стартует; восстановление из облака в такой ситуации требует ручной проверки, чтобы не затереть исправные данные.
- При переподключении после потери всей файловой системы хостинга сессия работает, только если предыдущие токены сохранились в облачной контрольной точке.
